# Design Notes

**Status (2026-08-30):** hero direction chosen and built (Full-Bleed Pin). Music/Shows/Book sections are placeholders — real content not written yet. See `TODO.md`.

## Why this project exists

Doug plays saxophone in Guacamayo, a real, currently-gigging Chicago Latin/funk band ("Funky Latin Groove"). This is a personal project, not client work — partly to give the band an actual site, partly to see how fast/awesome a site can get built with Claude Code end to end.

## The band's real assets — use these, don't reinvent

Guacamayo already has a consistent, professionally-made visual identity from designer/drummer Javier Saume Mazzei (`@javchisau`), seen across 7 promo YouTube shorts and shared directly as source files:

- `src/assets/logo.png` — the real wordmark lockup (chunky rounded "GUACAMAYO" bubble lettering, gold fill, black outline, red-orange bevel) with the circular macaw-head icon mark above it.
- `src/assets/flyer.jpg` — the real Reggies Chicago show flyer: a painted macaw (teal/turquoise face, orange-red-yellow wing gradient) on dark charcoal with a warm sunburst glow, "GUACAMAYO / FUNKY / LATIN / GROOVE" in groovy 70s-funk bubble lettering (gold/orange/teal/cream), aged paper texture.

Real lineup (from the flyer): Doug Rosenberg — saxophone, Jack Zará — bass, Manuel Reyes — guitar, Javier Saume Mazzei — drums.

There's also a real promo video (`GuacamayouFirstVideo.mp4`, an animated logo-reveal/intro clip) used in some exploration passes — not yet pulled into the actual site build.

## Design tokens — locked

`src/styles/tokens.css`, defined via Tailwind v4's `@theme` (so every value below is also a Tailwind utility — `bg-ink`, `text-gold`, `font-display`, etc. — change the file, everything updates):

- **Color**, sampled directly from the real flyer: `--color-ink #1c1712` (charcoal ground), `--color-paper #e9daaf` / `--color-paper-2 #f4ebd2` (aged paper, two warmths), `--color-gold #d9a441` ("GUACAMAYO"), `--color-orange #e2622c` ("FUNKY" / macaw wing), `--color-teal #2c8c87` / `--color-teal-deep #1b5551` ("LATIN" / macaw face), `--color-rust #b8431f`, `--color-red #c23b22`.
- **Type**: `--font-display` = Luckiest Guy (the groovy bubble face, matches the flyer lettering), `--font-display-alt` = Passion One (secondary bubble weight, used for section headings), `--font-body` = Archivo, `--font-mono` = Space Mono (labels, dates, utility text).

No serif anywhere, deliberately — this is a loud, playful, mascot-brand identity, not an editorial one.

## How we got here — the exploration trail

Chronological, all archived in the sibling `ui-lab` repo (`ui-lab/artifacts/guacamayo-band/`) so rejected ideas aren't lost:

1. **`ten-directions.html`** — first pass, 10 unrelated aesthetic universes (city pop, faceted-shatter, arcade neon, hanko-stamp, Japanese-design-trend crossovers, etc.), checked against Doug's other 4 sites for differentiation. **Rejected** — Doug wanted the band's own existing loud flyer palette instead of an invented identity.
2. **`ten-flyer-variations.html`** — 10 compositions locked to the real flyer's own palette/lettering (screen-print, marquee, ticket stub, wall-of-flyers, split-flap, etc.) instead of new palettes.
3. **`ten-hero-openings.html`** — same 10 rebuilt using the *real* logo PNG and flyer JPG (not recreated approximations), identical copy across all ten so only composition was being compared.
4. **`ten-full-page-backdrops.html`** — the real design problem: a photographic background behind real body text hurts legibility. 10 different solutions (tile-and-dim, fade-to-flat, duotone, ghost watermark, vignette window, vertical spine, bleed-past-nav, progressive-duotone-fade), built as scrollable previews using a sticky-background CSS technique so the backdrop persists past the hero into real content sections.
5. **`ten-video-backdrops.html`** — same problem, with the real promo clip in motion. Two ideas here don't exist in the image set: a freeze-frame-until-hover hero (mobile-data-conscious by design) and a real split-screen with footage on one side.

**Chosen: No. 02 from set 4, Full-Bleed Pin** — one full-bleed print of the flyer pinned behind the whole page via `position: sticky`, with a dark gradient scrim for legibility. Implemented in `src/components/PageBackdrop.astro`.

Doug's other four sites (dougrosenberg.com, dougrosenbergdev.com, haxbyte.com, arborkin.com) are all fairly restrained/moody — this project was explicitly built to be loud and maximalist instead, so it doesn't rhyme with any of them.

## Concrete choices — locked and built (2026-08-30)

- **Backdrop:** `PageBackdrop.astro` — flyer image pinned via sticky positioning + negative-margin content trick, so it stays visible through the hero and only gets covered once a section with its own opaque background (`bg-ink`) scrolls over it. As of 2026-08-31, a slow (28s) Ken Burns scale/pan drift via `motion-safe:animate-[backdrop-drift_...]` — the macaw reads as alive instead of static. Deliberately subtle (scale caps at 1.045, pan under 1%) so it doesn't read as an obvious slideshow; `motion-safe:` means `prefers-reduced-motion` users get a fully static image, no extra markup needed.

**Backdrop extended behind the whole page + glass sections, matched to nav colors (2026-08-31, direct feedback — "I definitely do not like the bottom half of the app being dark"):** every section below the hero was solid `bg-ink`, so the backdrop's sticky pin (only ever active for one viewport's worth of scroll, by design — see above) genuinely disappeared for the rest of the page, leaving a flat dark wall. Fixed by switching `PageBackdrop.astro` from `position: sticky` + negative-margin content to plain `position: fixed` — sticky can only stay pinned within its own normal-flow box, which was capped at `h-dvh` (one viewport); fixed just stays put behind the entire page automatically, no flow-box height to manage, and `main` no longer needs the negative-margin trick since a fixed element never occupies flow space to begin with. Each section (`About`, `Music`, `Shows`, `Press`, `Booking`) traded its opaque `bg-ink` for two stacked `absolute inset-0 -z-10` layers: a `bg-ink/85 backdrop-blur-md` base (still overwhelmingly dark/opaque — this is what keeps the backdrop from just showing through clearly, and is most of what keeps text legible) plus a `bg-{color}/8` tint using that section's own nav-tile color (gold/orange/teal-deep/paper2/rust) at very low opacity, so each section reads as a distinct, on-brand glass pane rather than a uniform dark field, and you can just make out the blurred flyer texture behind everything instead of it vanishing. **Known gap:** contrast was checked visually across every section at both desktop and mobile widths, not with the same hand-computed WCAG contrast-ratio math used earlier in this project (`QUALITY_CHECKLIST.md`) — that math assumed a flat, known background color, which no longer strictly holds once text sits over a translucent, blurred, moving image. The 85%-opacity ink base plus the image's own heavy darkening filter (`brightness(.6)` plus the existing gradient scrim) bounds the risk, but a real recheck is worth doing before calling this launch-ready.
- **Shows date tiles:** the split-flap treatment from `ten-flyer-variations.html` (gold/orange, real flyer colors) applied to the real date badges — each day digit gets its own tile, flapping into place once via a real `IntersectionObserver` the first time it scrolls into view, not looped forever (these are dates people read repeatedly, not a novelty marquee). `prefers-reduced-motion` skips the flip entirely and just shows the tiles flat.
- **Hero:** real logo (large — bigger than the original prototype sizing, per direct feedback), "FUNKY LATIN GROOVE" in the flyer's own three colors, evergreen tagline ("Live in Chicago" only). **Deliberately no specific show info (venue/date) in the hero** — that goes stale and belongs in the Shows section instead.
- **Nav:** as of 2026-08-31, a real global persistent nav — `Nav.astro` renders once from `Layout.astro` (not per-page, not nested in Hero anymore) as `position: fixed`, so it stays visible across the whole scroll instead of leaving with the hero. Restrained glassmorphism (`bg-ink/40` + `backdrop-blur-md`, no bright frosted panel/glow border) — a deliberate ask despite glassmorphism being named in `career-development`'s own checklist as a generic AI-site tell; kept tied to the real palette instead of a generic default. Real logo (not just text) top-left, linking home. All link hrefs are prefixed with the home path (`/guacamayo-band/#about`, not bare `#about`) so they still resolve correctly from non-index pages like `404.astro`. `html { scroll-padding-top }` in `global.css` keeps anchor-jump targets from landing hidden under the fixed bar. **Mobile note:** adding the real logo image pushed the link row past fitting at 375px on the original spacing; tightened mobile-only gap/tracking/logo-size to fit comfortably ≥375px, with the existing `overflow-x-auto` handling the rare <375px case gracefully (a few px short at 320px, not a hard break).

**Colorful flap-tile links (2026-08-31, "max out the coloration" prototype pass):** each nav link is now its own solid-color badge, reusing the same five-color split-flap cycle as the Shows/`ten-flyer-variations.html` exploration — gold/orange/teal-deep/paper2/rust. No resting-state motion (explicitly requested), but real hover/active/focus states: hover gives a slight 3D tilt (`rotateX`) + scale-up + brightness lift, scoped to `@media (hover: hover) and (pointer: fine)` so touch devices never get a stuck hover; `:active` reverses the tilt and dims, which is what mobile taps actually get. Added a `:focus-visible` ring, which the plain-text nav never had. Text color per tile came from a real computed-contrast check, not eyeballed — ink text passes on gold/orange/paper2, but fails WCAG AA at this text size on the brighter `--color-teal` (4.41:1) and on rust (3.27:1); swapped to `--color-teal-deep` + paper2 text (7.17:1) and rust + paper2 text (4.57:1) instead. **Real tradeoff, not hidden:** the colored tiles need more horizontal room than bare text did, so mobile now genuinely relies on the `overflow-x-auto` horizontal scroll below ~390px rather than fitting outright — acceptable for an explicitly-labeled prototype pass, worth reconsidering if this becomes the final direction.

**Nav-tile interaction redesign (2026-08-31, direct feedback on the shipped prototype):** the `rotateX` + `perspective` hover tilt above surfaced a real unwanted vertical scrollbar on hover — `overflow-x-auto` alone leaves `overflow-y` computed as `auto` too per the CSS spec (when one axis is a scrolling value and the other is `visible`, the UA computes the visible one as `auto` as well), and the 3D tilt was pushing the tile row's effective scroll height past its own box. Fixed by dropping the 3D tilt entirely — hover is now a flat `scale(1.06)` + `brightness(1.12)`, no `rotateX`/`perspective`/shadow — and by explicitly forcing `overflow-y: hidden` on the tile row as a belt-and-suspenders guard regardless of future transform changes. Click now sets a **persistent** "active" tile (real click-tracking `<script>`, not the momentary `:active` pseudo-class): the clicked tile gets `rotateZ(-6deg)` plus a static `box-shadow` ring, and stays that way until a different tile is clicked. The ring is intentionally not motion-dependent — under `prefers-reduced-motion`, the rotation is disabled but the ring stays, so which tab is "active" is never conveyed by motion alone.

**Real mobile menu, replacing the horizontal-scroll tradeoff (2026-08-31):** the `overflow-x-auto` fallback documented above was never actually solid — on a genuinely narrow viewport the five colored tiles (particularly the last one, "Book") could overflow past the visible edge with a real horizontal scrollbar, not just the "a few px short at 320px" case originally documented. Below the `sm` breakpoint (640px) the tile row is now a hidden dropdown panel (`position: absolute; top: 100%` under the fixed bar, since the bar's own `position: fixed` is already the containing block) toggled by a standard hamburger button (`sm:hidden`), morphing to an X via `aria-expanded` — no separate visual-only state to drift out of sync with what a screen reader announces. At `sm` and up the row reverts to the original always-visible inline layout; there's genuinely enough width there for five tiles, so no scroll fallback is needed on desktop anymore either. Clicking a tile closes the mobile menu (same-page anchor jump shouldn't leave the panel sitting open over the section it just jumped to) and still sets the persistent `rotateZ` active state from the fix above. `resize_window` remained unreliable in this environment tonight (confirmed via a fresh un-resized tab vs. a resized one showing inconsistent geometry) — verified breakpoint behavior instead with a fixed-width `<iframe>` and direct `getBoundingClientRect()`/`scrollWidth` measurement at 371px (mobile) and 896px (desktop), not screenshots of a resized window.

**"Book" still bled past the edge in production, and a real flip-card replaces the rotateZ skew (2026-08-31):** despite the fix directly above, a real production screenshot at a genuine narrower-desktop width (not tested in the previous pass — only ~896px was spot-checked) showed the row bleeding past the viewport with a real page-level horizontal scrollbar. Root cause: removing `overflow-x-auto` from the row for the ≥640px case also removed its load-bearing side effect — per the flexbox spec, a flex item's automatic minimum size is its content size *unless* `overflow` is something other than `visible`, in which case it's treated as 0. Every tile is `shrink-0`/`whitespace-nowrap`, so without that the row refused to shrink below the sum of all five tiles' widths. Restored `overflow-x: auto` on the ≥640px row (mobile's dropdown panel doesn't need it, it's a vertical stack) and this time verified across a swept range of real widths (640–1200px via a fixed-width `<iframe>`), not one spot-check. Separately, direct feedback rejected the `rotateZ` skew entirely in favor of "a fun flip animation" — rebuilt as a real front/back flip card per the CSS-Grid-stacking technique from [Smashing Magazine's "Magic Flip Cards And The Common Sizing Problem"](https://www.smashingmagazine.com/2020/02/magic-flip-cards-common-sizing-problem/) (both faces occupy the same grid cell via `grid-area: 1 / 1` rather than being absolutely positioned, so the tile's size follows its own padding/min-h classes rather than whichever face happens to be showing). `.tile-flipper` rotates `rotateY(180deg)` on click; `backface-visibility: hidden` keeps whichever face is edge-on from showing through. The "back" (active) face is deliberately **not** each tile's own colors inverted — three of the five tiles (About, Music, Press) pair a color with ink, and an inverted fg/bg would put ink-on-ink exactly where the nav's own background is ink, making those three tiles' active state visually disappear into the backdrop (caught by actually clicking through every tile during testing, not assumed). Instead every tile's back face uses one consistent paper2-background/ink-text look (the same real contrast pairing already verified for Press's own resting colors) plus a checkmark and an `inset` ink ring — the ring specifically because Press's resting colors already happen to be paper2/ink, so without it Press's "activated" state would read as nearly identical to its resting state.

**Hover-triggered flip, X axis instead of Y, JS state dropped entirely (2026-08-31):** the click-persisted flip above still had a real bug — the last tile's `scale(1.06)` hover effect grew its box past the row's own edge and surfaced a genuine horizontal scrollbar on hover, only visible on whichever tile happened to sit at the row's boundary. Direct feedback rejected the Y-axis spin outright ("vertical axis not horizontal axis" — read as: match the site's own established flap-board motion, `rotateX`, the same axis `Shows.astro`'s date tiles already flip on, not a Y-axis card-spin) and asked for the flip to trigger on hover rather than click, with hover reading as simply "brighter." That request happens to fold both fixes into one: `scale()` is gone from hover entirely (only `filter: brightness(1.2)` remains, which doesn't touch layout and can't reintroduce the scrollbar), and since a flip that's purely a hover response reverts the instant the pointer leaves, there's no more reason for it to be JS-tracked, persistent state at all — `.tile-flipper`'s `rotateX(180deg)` is now driven directly by `:hover`/`:focus-visible` in CSS, and the click-handler that used to set `.is-active` is gone (a tile click now only closes the mobile dropdown, nothing else). `:focus-visible` gets the identical flip + brightness outside the `hover: hover` guard, since keyboard users tabbing through a page never trigger `:hover` at all — without that, this flourish would be invisible to them entirely. On touch, no `:hover` ever fires, so tiles simply show their front face and navigate normally on tap, same as they always did. Global `scroll-behavior: smooth` was added at the same time (`global.css`, gated behind `prefers-reduced-motion: no-preference`, the standard accessible-safe pattern — off unless the visitor hasn't asked for reduced motion) so anchor-jump navigation reads as a real scroll rather than an instant cut.

**Hover-clip bug fixed, real "current section" state added back (2026-08-31):** direct feedback caught a real rendering bug — hovering visibly clipped/glitched at the tile's edges, hard to even screenshot since it only showed mid-animation. Root cause: `.tile-face { border-radius: inherit; }` inherits from its actual DOM parent, `.tile-flipper` — which never set `border-radius` at all, so faces were rendering perfectly square while `.nav-tile` itself was rounded via Tailwind's `rounded` class; the mismatch showed as a seam during the 3D rotation. Fixed with explicit matching `border-radius: 0.25rem` on both, plus `overflow: hidden` on the outer, non-transformed `.nav-tile` box so anything from the 3D children is hard-clipped to one stable rounded rect regardless of what the animation is doing mid-flip.

Separately: dropping the JS click-tracking system for the hover-only flip (previous entry) also dropped the only thing that had been indicating "which section are you currently on" — a real gap, since hover is transient and can't do that job (it only reflects where the mouse happens to be, not where the page is scrolled to). Added a proper scroll-spy: an `IntersectionObserver` per section (ids read straight from each tile's own `href` rather than a second hardcoded list, so the two can't drift apart) with `rootMargin: "-45% 0px -45% 0px"` — shrinking the observed area to a thin band vertically centered in the viewport, so exactly one section counts as "current" at a time instead of two adjacent ones both reporting visible during the scroll between them. The indicator itself is a small underline (`.current-mark`, in `--tile-fg`) that grows in from center via `width` transition — deliberately a plain sibling of `.tile-flipper`, not a child of it, so it sits still on top of whichever face is showing rather than getting caught up in the 3D rotation, and reads as a stable "you are here" marker independent of hover state.

**The clip fix above didn't actually fix it — real cause was a width mismatch, not the radius (2026-08-31):** direct feedback caught that the flipped face was *still* visibly clipping text (an "About" tile losing the tail of its "T"). Measured it directly: the back face's natural content width ("✓ About") was 59px, but the grid-stacked tile was only rendering it at 55px — the CSS-Grid "both faces share one cell" sizing technique wasn't actually expanding the track to the wider of the two stacked faces the way the Smashing Magazine technique assumes it should, for reasons not fully root-caused (tried removing the `overflow: hidden` from the previous fix in isolation — same 55px, so that wasn't the cause either). Rather than fight the grid-sizing quirk, removed the actual source of the mismatch: the checkmark. Direct feedback agreed it wasn't earning its keep ("I see no reason to have the checkmark in there") — the paper2/ink face + ink ring already reads as clearly "activated" on its own. Both faces now render the exact same label text, so front and back are pixel-identical in width by construction; verified all five tiles' front/back widths now match exactly (38.2px × 4, 30.6px for Book), and the clip is gone.

**The underline retired for a glassy resting state + a glow, and the flip now plays on scroll too (2026-08-31):** direct feedback: "I'm not crazy about the underline. What would a small visual element to add to the active state besides increased opacity?" — offered a soft color glow as the recommended alternative (asked via `AskUserQuestion`, since it's a real design call), which was picked. Resting tiles (`.tile-face-front`) now use `background: color-mix(in srgb, var(--tile-bg) 65%, transparent)` plus `backdrop-filter: blur(6px)` — thinning and blurring just the *background*, not the whole face, so the label text stays fully opaque and legible while the tile itself reads as glassy/muted. `color-mix` over a literal rgba value specifically so the translucent tint is still derived from each tile's own `--tile-bg`, not a second hardcoded color to keep in sync. The current section's tile drops back to its full solid color plus `filter: brightness(1.1) drop-shadow(0 0 8px var(--tile-bg))` — brighter, no longer glassy, glowing in its own color. The glow is `filter: drop-shadow`, deliberately not `box-shadow`: `.nav-tile` has `overflow: hidden` (needed for the flip-clip fix above), and `box-shadow` gets clipped by an element's own `overflow`, while `filter` output isn't — confirmed the glow visibly escapes the tile's rounded edges rather than being clipped flat. Separately, added a one-shot flip-pulse (`rotateX(0deg)→180deg→360deg`, landing back on the front face) that plays via a JS-toggled `.is-pulsing` class exactly when the scroll-spy hands a *different* tile the current state — deduped against the previously-current tile so scrolling back to an already-current section doesn't replay it. Ties the nav into the same flap-board motif the Shows date tiles already use on scroll-into-view, rather than introducing a second unrelated motion language. `prefers-reduced-motion` skips the pulse animation entirely (checked once via `matchMedia`, not per-flip) while the persistent glow/brightness/glassiness — none of which are motion — still fully apply.

**Real double-flip bug in the pulse, plus more glassiness (2026-08-31):** direct feedback caught a genuine bug — a visible second flip right after the scroll-triggered pulse. Cause: the pulse used a separate `@keyframes` `animation`, and `.tile-flipper` also has a `transition` on the same `transform` property for `:hover`; when the pointer happens to be resting on a tile as its pulse ends (a common case — scrolling doesn't move the cursor), the animation's end and the transition's own target collide, producing a second, disjointed flip. Verified by sampling `getComputedStyle(...).transform` every 100ms with the tile genuinely hovered (`computer` tool, not a dispatched event — those don't trigger real `:hover` matching) through a scroll-triggered pulse: before the fix this showed a jump; after, the matrix stayed rock-steady the whole time. Fix: dropped the `@keyframes` entirely — `.is-pulsing` now just sets `transform: rotateX(180deg)`, the *same* target `:hover` already uses, riding the *same* `transition` instead of a competing `animation`. JS swapped its `animationend` listener for a plain `setTimeout(420ms)` since there's no longer an animation event to listen for. Also bumped the glassy resting state further per request: `color-mix` 65%→55% opacity, `backdrop-filter: blur` 6px→8px.

**A second, real bug: the current tile got stuck forever once set (2026-08-31):** a screenshot showed the URL and page both saying `#about`/scrolled to the very top, yet "Music" was still glowing as current — the scroll-spy only ever *added* `.is-current` on a section entering the observed band, never removed it on exit. Scroll back up above every section (into the Hero, where nothing should be current) and whatever was last current just stays that way permanently. Fixed by handling the `!entry.isIntersecting` case too: if the section that exits the band *is* the currently-tracked tile, clear it — a different section entering in the same observer callback batch still overwrites this correctly via its own branch, so normal forward/backward scrolling between sections is unaffected, only the "scrolled above everything" case changes. This is a distinct bug from the animation/transition double-flip fixed above, not the same root cause, though both were visible in the same round of feedback. Verified with a `MutationObserver`-based class-change logger (not guessed): scrolled through all five sections then all the way back to the top — every section pulsed exactly once, and after returning to the top, all five tiles report `is-current: false`, none stuck. (Also hit a real environment dead end while verifying this: `IntersectionObserver` stopped firing entirely in the browser-automation tab — even for `document.body` on an unrelated site — after enough reuse across this session's tests; a genuinely fresh tab group resolved it. Not a site bug, but worth knowing if a future session's automated checks go inexplicably silent.)

**Double-flip persisted after both fixes above — a third, distinct cause (2026-08-31):** direct feedback (with a screen recording) confirmed the double-flip was still happening even after the animation/transition fix and the stuck-tile fix. Neither of those was the mechanism for the specific case a person actually hits: **clicking** a nav tile. A click starts with the pointer already on the tile — `:hover` is already flipping it — and the click triggers a scroll (smooth, per the earlier `scroll-behavior: smooth` addition) to that section. In real use the pointer commonly drifts off the tile sometime during that scroll, well *before* the section actually crosses into the scroll-spy's thin observed band — so hover ends (flips back to flat) and the spy's own pulse fires moments later (flips again): two independently-correct flips with a gap between them that reads as one confusing double-flip. Fixed by tracking `recentlyClickedTile` and suppressing the spy's pulse for whichever tile was just clicked (a 2s window, long enough to cover a scroll to any section on the page) — the click's own hover-flip already delivered the feedback once, so the spy doesn't need to repeat it. Organic scrolling (mouse wheel/trackpad, not clicking a nav link) is completely unaffected by this — `recentlyClickedTile` stays null the whole time in that case, so those pulses fire exactly as before.

**Could not fully verify this one via automation** — hit a real coordinate-space mismatch between the browser-automation screenshot's pixel dimensions and the page's CSS pixel space (not constant; had to recompute the scale factor from a fresh screenshot each time), and separately, a synthetic click on the nav tile updated the URL hash but did not trigger the browser's native scroll-to-anchor behavior the way a real click does. Given several confirmed environment-flakiness incidents in this same session already (`resize_window`, `IntersectionObserver` going dead, timer throttling in a backgrounded tab), this reads as more tooling flakiness than a real second bug, but it means this specific fix is reasoned from a solid mechanism, not confirmed end-to-end by a passing automated test — worth an explicit real-browser check.

**"Carnival" palette shipped, backdrop brightened to match (2026-08-31):** picked from the four-option comparison (a real side-by-side artifact, not just described — see the `ui-lab` local archive) in favor of a brighter, more Afro-Caribbean, red-forward direction over the original flyer-sampled brown/gold palette. `tokens.css` rewritten with the new hexes; `--color-paper` and `--color-rust` dropped entirely rather than left unused — grepped the whole `src/` tree first to confirm neither had any real remaining usage (paper never did; rust's one use, `Booking.astro`'s section tint, moved to the new `--color-red` alongside Book's nav tile, which also moved from rust to red). Re-ran the same real WCAG contrast script used earlier tonight against the new hexes rather than assuming the old pass/fail conclusions still held — they didn't: paper2 text on the new red only reaches 3.38:1 and fails at this text size, so Book's tile now uses ink text (5.13:1), unlike every other tile's fg color, which stayed the same role. Separately, direct feedback that the real YouTube clip thumbnails read as "very bright" while the page backdrop still read brown prompted dropping the backdrop image's filter chain from `sepia(.15) saturate(1.2) contrast(1.05) brightness(.6)` to `saturate(1.4) contrast(1.08) brightness(1)` — sepia specifically pulled everything toward brown/muted regardless of the token palette underneath it, so it had to go, not just get tuned down. Strengthened the gradient scrim slightly (`from-ink/15 to-ink/60` → `from-ink/20 to-ink/70`) to keep Hero's own text legible against the now much brighter, unfiltered image.

**Nav tile flip: white face nixed, then the flip itself briefly dropped, then brought back with a different destination (2026-08-31):** direct feedback rejected the paper2/ink "back face" outright — first read as "drop the flip entirely, just get brighter/glowing/larger on hover" (built and shipped that: single-face tile, no more `.tile-flipper`/`.tile-face-front`/`.tile-face-back`, just `.nav-tile` itself transitioning `background`/`backdrop-filter`/`filter`/`transform`), then corrected to "no, retain the flip motion, just change what it flips *to*." Rebuilt the flip-card structure (front/back faces, `perspective`, `backface-visibility`, the explicit-not-`inherit` border-radius and `overflow: hidden` clip-fixes from earlier rounds all still apply) with the back face now the tile's *own* color at `brightness(1.3)`, not paper2/ink — the flip itself is the "different state" signal now, not a hue swap. Front and back render identical label text this time (no checkmark), so the width-mismatch clip bug from an earlier round structurally can't recur. Glow (`filter: drop-shadow`) lives on `.nav-tile`, not the back face — `.nav-tile` has `overflow: hidden`, and an ancestor's overflow clips a *descendant's* filter output same as anything else, so a drop-shadow on the face itself would just get clipped away; a filter on the element that owns the overflow isn't self-clipped. Hover and `.is-current` both drive the identical `rotateX(180deg)` + `scale(1.05)` + glow target, and — as a real side effect of there being one unified CSS-only mechanism instead of a separate JS-timed pulse — this is what actually retired the double-flip bug for good, not another patch on top of the click-suppression fix. `ease-in-out` on every transitioning property per direct request. Reduced-motion keeps all the state changes (flip/glow/scale still apply, since the brighter styling only exists on the back face and removing the rotation would leave those users with no signal at all) but drops the animated transition, matching the guidance's actual intent (no animated motion, not no state).

**Backdrop drift given a Z-axis rotation too, real gap bug caught (2026-08-31):** direct ask, with the exact CSS already written — `rotate(-4deg)`/`rotate(4deg)` added to the existing `backdrop-drift` keyframes (bare `rotate()` in a 2D context already means `rotateZ()`, no separate property needed). The proposed scale values (`1.02`/`1.08`, up from the original `1`/`1.045`) weren't enough overscan for the new rotation, though — confirmed with a real visual test (freezing the wrapper's `transform` at the `0%` keyframe's exact value and screenshotting) showing a genuine black gap at the top and bottom edges on a wide viewport. The math: covering a rotated box's original bounding box needs roughly `cos(θ) + aspectRatio × sin(θ)` scale, and at θ=4° with a ~2.3-2.5 wide-desktop aspect ratio that's already ~1.17-1.2, nowhere near 1.02. Raised both keyframe waypoints to `1.24`/`1.3` (same relative pulse, safe floor with margin), re-verified at both rotation extremes on a wide viewport (1536-1568px, clean) and in a 390×844 portrait iframe (the other extreme aspect ratio, also clean).

**Parrot moving independently of the rest of the backdrop — masked-layer fake, not a real cutout (2026-08-31):** direct ask, explicitly framed as an experiment to keep only if it works ("try it out and revert if its a dead end"). There's no real isolated parrot asset — `src/assets/` only has the single flat `flyer.jpg` and the unrelated small mascot `logo.png` — and no image-segmentation tool available to cut a clean one out. Offered three options (provide a real cutout PNG / fake it with a CSS mask / skip it); picked the fake. Built as two full copies of the *same* `flyer.jpg` (`.backdrop-base`, `.backdrop-parrot`), each with an opposite-direction soft `mask-image` left/right split (`linear-gradient`, same masking technique as `.section-glass-fade`) so one shows everything except roughly where the parrot sits and the other shows only that region, blended through a ~20%-wide soft zone rather than a hard line. The mask stops are calibrated against the parrot's actual *on-screen* position in this crop (`object-[82%_34%]`), not the source file's own pixel coordinates — object-fit/position change how those two relate at every viewport size, so anything traced from the raw 1200×1600 file would drift out of alignment on screen; confirmed this by opening the source file directly and comparing it against real rendered screenshots. The parrot layer's mouse/scroll tilt is amplified 1.8× over the base layer's — real parallax depth relies on the closer/foreground element visibly moving more than what's behind it, not just moving differently for its own sake. Verified with real mouse events at both extremes (top-left, right-center) plus rest position: no black gaps at the seam (needed extra overscan on the parrot layer, `scale(1.3)` vs the base's `1.15`, for the same reason the earlier rotation fix needed one), and the parrot visibly shifts relative to the "GROOVE" lettering behind it in each screenshot, confirming the illusion actually reads before calling it done. Known real cost, not yet addressed: this renders the same large image twice (`astro:assets` processes each `<Image>` separately), which the project's own standing image-optimization TODO item should account for once a real cutout asset replaces this hack.

**Parrot layer given translateZ (2026-08-31):** direct question ("is there a translateZ CSS property?") followed by "try it." Added `translateZ(60px)` to `.backdrop-parrot`, both in the static CSS (rest/reduced-motion state) and the script's per-frame transform string — needed in both places since the script's inline `style.transform` overwrites the CSS rule's value entirely once it starts running, not just adds to it. Works because the outer fixed container already has `perspective: 1200px` set (from the earlier tilt work) — translateZ does nothing visible without a perspective context on the element or an ancestor. Re-verified the overscan margin still holds with this added: no gaps at either mouse corner extreme, and at the combined worst case (mouse in a corner *and* scrolled to the very bottom, stacking the scroll-tilt and mouse-tilt contributions together).

**Backdrop zoomed out — trimmed the stacked overscan margins (2026-08-31):** direct feedback — "zoom the image out so I can see more of it." The apparent zoom wasn't one setting: `object-cover` on this tall (1200×1600) poster against a wide/short viewport already crops most of the image's height by itself, and every overscan margin added across the tilt/rotation/parrot work this session (`backdrop-drift`'s `1.24`/`1.3`, `.backdrop-tilt`'s `1.15`, `.backdrop-parrot`'s `1.3`) is a nested `transform: scale()` that *compounds* with the others (nested elements' scales multiply), so the real effective zoom was considerably higher than any single number suggested. Those values had real margin built in beyond their calculated minimums, though, so there was room to trim: dropped to `1.1`/`1.14` (drift), `1.08` (tilt/base), `1.15` (parrot) — noticeably more of the poster visible (more of "GROOVE," more of the parrot's beak/wing) without reasoning it through by hand alone. Re-verified the exact same worst cases as every prior overscan check this session: both Z-rotation keyframe extremes frozen and screenshotted, and mouse-corner + scrolled-to-bottom combined — clean at all of them, no gaps reappeared.
